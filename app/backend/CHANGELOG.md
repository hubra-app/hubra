# Changelog

All notable changes to this project are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

section and position, or the apps show that version in English.

## [Unreleased]

### Added

- **Booking contract without a category, and checks the member**: `finance.transaction.create`: `category_id` is optional now (Kasse pays expense claims that have none), and an unknown or archived `member_id` is refused instead of booked. docs/contracts.md.
- **Finance contracts for bookings**: plugins can put a booking in the books with the new action `finance.transaction.create` (needs `finance.transactions.create`), and `finance.invoice.set_status` takes a `payment` (date, amount, method) that gives the invoice's booking what arrived, or books the income when nobody booked the invoice. Bank Import uses both instead of writing the bookings itself, so marking an invoice paid by hand or booking a bank line now needs the finance rights. docs/contracts.md. <!-- for: staff -->
- **One database role per club**: inside a club (requests, background jobs, per-club scheduled jobs) the database connection now runs as the club's own Postgres role, with no rights on other clubs' schemas or on the template tables in public, so a query that reaches for another club's data fails instead of returning it. The init step (`flask sync-tenant-schemas`) creates the roles of existing clubs. Operators: the app role needs `CREATEROLE` (`ALTER ROLE hubra_app CREATEROLE;` or run scripts/pg-app-role-upgrade.sh again); without it nothing changes. docs/club-db-roles.md. <!-- for: staff -->
- **Backup retention in manage**: manage › Backups › Settings › **Retention** sets how many daily, weekly and monthly backups each set keeps (the global one and each club's), how many days manual backups stay, and how many days the backups of a club deleted for good stay. Defaults: 7 daily, 4 weekly, 12 monthly (was 6); manual backups are deleted after 90 days and the backups of deleted clubs 30 days after each was made (before, both stayed until someone deleted them; 0 keeps that). Pruning deletes the bucket object too. docs/disaster-recovery.md. <!-- for: staff -->
- **Largest file per plan and per club**: each plan has a **Largest file (MB)** (All clubs › Plans & prices), and a club can have its own (club page › Limits › Adjust). A plan without one uses the platform's `files.max_mb` (25 MB), as before. Uploads may be up to `MAX_UPLOAD_MB` (env, default 100; backend and the frontends' nginx), other requests stay at 25 MB. Plugins read the club's size with `files.max_mb()`. Needs `flask db upgrade` (new column `platform_plans.limit_file_mb`, runs by itself after the deploy). <!-- for: admins -->
- **Anlässe as a month**: Anlässe has a **Liste / Monat** switch; the month shows each day's events in their type colour and opens an event with a click. On a phone the days show dots and the picked day's events are listed below. The read confirmation ("Gelesen, bestätigen", "N bestätigt") and the scheduled badge now also show on a post's own page. New endpoint `GET /events/<id>/participants` (events.read): the names of members who hold a place or said "Vielleicht", for every member who may see the event; waitlisted, pending and declined sign-ups stay with the organisers. <!-- for: events -->
- **Anlässe, Beiträge and Umfragen reworked**: Anlässe is a list grouped by month with one sign-up button per event; organiser actions (roll call, edit, template, cancel, delete) sit in a ⋯ menu, and a filter shows only the events you signed up for. Anwesenheit and Schnuppern are tabs of Anlässe now, and plugins can add tabs there (Booking adds **Vor Ort**). Beiträge shows a banner for must-read posts you haven't confirmed, puts them first, and has a search and a filter. Umfragen shows open polls first, marks the ones you still have to vote on, lets you change your vote, and shows the results only after you vote (whoever runs a poll sees them all along). Each event has its own page (click its title): date, place, description, signing up and a link to share; organisers also see who signed up and take the roll there.
- **Language of the platform Discord bot**: manage › Discord › Settings › Platform log has a **Bot language** switch (Deutsch or English). Everything the bot writes on the platform's own Discord server follows it: audit entries, alert buttons and footers, the daily overview, Hubra release notes, security pings, the replies to `/plattform` and `/wartung`, and the support threads. Default stays Deutsch; club servers keep following each club's language. docs/discord.md. <!-- for: staff -->
- **Groups give roles, group functions, default and tier groups**: a group can give roles (Gruppe › Bearbeiten › "Gibt die Rollen"): everyone in it holds them for the whole club while they are in it. Owner and admin roles can't be given this way, and an open group gives none. A function can be a group function (Trainer/in): it is filled per group on the function's page or the group's new Funktionen tab, and its roles count in that group only. A group marked "Neue Mitglieder kommen in diese Gruppe" gets every new member; a tier can name groups its members are in (on the tier or the group), and a tier change moves them. Needs `flask db upgrade` (runs by itself after the deploy; new tables `group_roles`, `tier_groups`, columns `functions.per_group`, `function_holders.group_id`). docs/roles.md, "Groups". <!-- for: groups, admins -->
- **Quiet hours** (SSO › Mein Konto › Benachrichtigungen › Einstellungen): push and Discord direct messages from every club wait until the night is over; the bell and mails come as always. See docs/notifications.md.
- **One letterhead for every PDF**: invoices now carry the club's letterhead (logo, name, address, website, contact line, page numbers, primary colour); plugins get the same through the `pdf.render` action. <!-- for: finance -->
- **Plugin data in the privacy export and deletion**: modules and plugins that keep more about a member than rows linked to them (files, data in another service) now offer `<module>.privacy.export` and `<module>.privacy.erase`; the export lists it under `modules`, and a deletion stops if one of them can't delete. See docs/contracts.md. <!-- for: admins -->
- **Translation coverage** (Übersetzungen): how many texts each language has, for Hubra and every plugin, with the missing ones listed and a button to suggest each. <!-- for: admins -->
- **Kassen-Cockpit**: a new dashboard can start from a template; the first one, for the treasurer, shows money today, expected income, open invoices by age, budget use and open expense claims. New widgets **Offene Rechnungen nach Alter** and **Erwartet diesen Monat**. <!-- for: finance -->
- **Confirm risky club actions**: changing the bank details, giving admin rights and deleting a member for good now ask for your password or passkey first; the confirmation counts for ten minutes. <!-- for: admins -->
- **Export all my data** (support site › Meine Daten): **Alles als ZIP** downloads the account plus, per club, what that club keeps about the member, in one file.
- **Session notes on event dates** (Anlässe › Anwesenheit): trainers note what was trained, a note for the next trainer and a guide link per date; the next date of the series shows them as **Letztes Mal**. Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: events -->
- **Comment moderation** (Beiträge): members report a comment from its menu. Moderators (the role right *Moderate posts and comments*) see how often a comment was reported, can hide it, show it again or keep it, and can mute a member in comments for 1 to 30 days. Club-wide moderators get a **Moderation** box above the posts. Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: posts -->
- **Check-in with the member badge**: plugins can ask which club member has a member badge number (contract `members.badge.lookup`, docs/contracts.md). The Keys plugin uses it so a check-in scans the badge from My Account or Google Wallet; the per-club member card goes away.
- **Soft member limit with the plan that fits** (club app, billing admins): near a plan limit a banner names the cheapest plan that fits, with its price, and switches to it in one click. At the member limit a grace period (manage › Settings › Limits, 14 days by default) lets new members still join before the limit holds; 0 days keeps the hard stop. <!-- for: admins -->
- **Member badge in Google Wallet** (sso › My account › Profile): an "Add to Google Wallet" button under the member badge saves it as a pass with the name, the badge number as QR code and the clubs. Hubra is the one issuer for every club; the pass follows joins, leaves and name changes and goes inactive when the account is deleted. Set it up in manage › Services › Google Wallet (docs/google-wallet.md). Operators: run `flask db upgrade` (new columns `users.google_wallet_object`, `users.google_wallet_hash`).
- **Post-deploy steps run themselves**: once every backend process runs a new build, a worker runs `flask db upgrade`, `sync-tenant-schemas`, `sync-permissions`, `seed` and `plugins sync` once for that build, unless an init step is already doing it. manage › Diagnostics › System health › Builds shows each step and the output of one that failed, with **Run now** to start them again; a failure also sends an upgrades alert. A platform setting (Diagnostics › Settings) turns it off. Operators no longer need to run these by hand after a release. <!-- for: staff -->
- **Problem reports carry the request ids**: "Problem melden" in the club app also sends the last ten API calls of the session (request id, method, path without query, status, error code). On the case in manage › Reports & ideas, **Last requests** lists them and links a failed one to its error group under Diagnostics › Errors. <!-- for: staff -->
- **Upgrade check for plugins**: manage › Plugin catalogue › Upgrade check lists the installed plugins whose `hubra:` range leaves out the Hubra version you are about to move to, whether a plugin update fixes it, and how many clubs use each. The release check (pull requests and the dry run) fails when an official plugin has no version for the new release. <!-- for: staff -->
- **Fee run preview**: Finanzen › Rechnungen › **Vorschau Beitragslauf** shows what the daily invoice run would bill on a chosen day, before it does: count, total, due date, a total per tier, every member with period and amount (pro rata, payment plan, no email address flagged), why members are skipped, and the last twelve months for comparison. Nothing is created. <!-- for: finance -->
- **Call an event off with a reason**: Anlässe › **Absagen** cancels an event with a reason (one tap on a common one, or your own). It stays in the calendar, marked and struck through; sign-ups close, no reminder goes out, and everyone signed up or waiting plus the event's group hear it with the reason (bell, push, messengers; a mail to those signed up). `event.changed` carries `cancelled` and `reason` for plugins and webhooks. **Doch durchführen** undoes it. Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: events -->
- **Event templates**: save an event (place, time, places, settings, description) as a template from its row in Anlässe, and start new events from **Aus Vorlage**: the form opens filled in, only the date is left. Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: events -->
- **Share a dashboard with groups**: the form to create a dashboard and ⋯ › Name und Sichtbarkeit set who sees it: Privat, Ganzer Verein or chosen Gruppen. A dashboard shared with groups shows only for their members. Needs `flask db upgrade` (new column `dashboards.group_ids`, runs by itself after the deploy).
- **Scheduled and expiring posts**: the post form has **Publish at** (the post stays hidden from members and goes out, with its notification, within five minutes of that time) and **Hide after** (members no longer see it after that time). Authors and whoever may edit the post still see both kinds, marked. Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: posts -->
- **Must-read posts**: tick **Lesebestätigung verlangen** on a post and members confirm it with one tap; whoever may edit the post sees who confirmed and who has not, and those missing get one reminder after a number of days (posts setting, 7 by default, 0 for none). Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: posts -->
- **Event end date, deadlines and von/bis time**: the event form has Enddatum (multi-day events), Anmeldeschluss and Abmeldeschluss (the app already enforced them, but nobody could set them), and Beginn/Ende time fields instead of free text. An old free-text time stays until a time is picked. The list shows the end date and the sign-up deadline. <!-- for: events -->
- **Edit open invoices**: Finanzen › Rechnungen › ⋯ › Bearbeiten (and on the invoice page) changes amount, due date and text of an open invoice. A paid invoice is locked; the API refuses changes to it until the payment is taken back. <!-- for: finance -->
- **Notice periods from the statutes**: Settings › Mitgliedschaft takes a notice period in months and the period end leaving takes effect at (month, quarter, half-year or year). A member who wants to leave sees the earliest exit date and their invoices still open; the board sees both on the request to leave. <!-- for: members -->
- **One calendar for all clubs**: sign-in › My account › Profile has a personal calendar link with the events of every club the person is in (or only those they signed up for), named with their club, for Google, Apple or Outlook calendars. **New link** stops the old ones. Cancelled events show as cancelled in calendar feeds. Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: events -->
- **Join and trial posters**: Members › Applications › **Plakat erstellen** prints an A4 poster or A6 flyer with a QR code for asking to join or booking a trial. A tag on each poster travels with the QR code, requests and trial bookings show where the person came from, and a table counts them per tag. Needs `flask db upgrade` and `flask sync-tenant-schemas` (run by themselves after the deploy). <!-- for: members, admins -->
- **"Out now" mails**: when a roadmap item ships, everyone who voted for it, or for or reported an idea linked to it, gets one short mail. What's new marks the items you voted for on their release ("You asked for this").
- **Support access in the club's log**: when Hubra support opens a club, its audit log shows who, as which member, why, for how long and whether they could change things, and when it ended. Settings › Club › **Support access only when approved** makes support ask first: the club's admins approve or decline the request, and an approval opens one session within 24 hours. Needs `flask db upgrade` (runs by itself after the deploy). <!-- for: admins -->
- **What's new for your club**: What's new in the club app leaves out changes to modules the club doesn't have or the reader can't use, changes only admins care about (for members) and changes for Hubra's own team.
- **Module and plugin usage**: manage › Plugin catalogue › **Usage** shows in how many clubs each module and plugin is on, in how many it was used in the last 30 days, where it is on but unused, and installed plugins no club uses. Counted every night, or at once with **Count now**. <!-- for: staff -->

### Changed

- **Sessions shows each sign-in once**: My account › Sessions lists your sign-ins (one per browser) and shows the clubs you opened from each as tags under it, instead of an extra row per club. Signing out a sign-in still ends its club sessions too, and a club admin can still sign a member out of the club. Needs `flask db upgrade` (new column `sessions.account_sid`, runs by itself after the deploy); club sessions from before the update keep their own row until they expire.
- **Dashboards as a grid**: dashboards and start pages are a grid of 12 columns: drag a widget's grip to move it, drag its corner to change width and height (or use the arrow keys), and "Höhe nach Inhalt" goes back to the content's height. Older dashboards keep their layout.
- **German texts reviewed**: German API errors that showed in English (dashboards, trial training, licences and modules, sign-in, connected apps and more) are now German; menu paths in hints point at today's pages (API & Webhooks, Mein Konto › Zwei-Faktor, Discord › Einstellungen, Alle Vereine › Tarife & Preise, Konto › Mitgliedschaft › Benachrichtigungen); one word per thing: Zahlungserinnerung (not Mahnung), Einweisung (not Einführung), Schnuppertraining, Gesperrt, Mobil, Inhaber/in, «» quotes. The German glossary for translators describes Standard German instead of the old dialect.
- **Vor Ort on the start page**: Dashboard › Persönlich shows "Heute vor Ort" (who is in which room today) while the Booking plugin is on, until the member changes the page. Clubs without Booking see the page as before.
- **Kommunikation in the sidebar**: a new sidebar area Kommunikation holds Mail and the plugins that reach members (Letters, Messengers, Inbox). Each person can still move entries or rename the area.

### Fixed

- **Dashboard widgets follow module access**: in a club that hides a module from some roles, members without that module no longer see its dashboard widgets or their data (the module's own API already refused them). Found in the Booking security audit (Vor Ort widgets).
- **Backend hardening, part 2 (rest of the backend image audit)**: plugin downloads connect to the address that passed the public-address check, and check every redirect the same way, so a second DNS answer can't send them into the local network. An OAuth sign-in code is claimed in one database statement, so two token requests racing with the same code can't both get a token. The public `/mail/health` asks the mail server at most once a minute per process. The OAuth issuer and the sign-in callback addresses come from one place (`API_PUBLIC_URL`); production warns at start-up when it is not set, since the request's Host header stands in then.
- **Backend hardening (security audit of the backend image)**: the image starts with `FLASK_ENV=production` unless a deployment sets something else, so a missing variable no longer means debug mode, random per-process secrets, a SQLite fallback and cookies without Secure (a deployment without `SECRET_KEY`, `JWT_SECRET_KEY`, `DATABASE_URL` or `FERNET_KEY` now stops at start instead). Signing in with an address that has no account takes as long as a wrong password, so the response time no longer tells which addresses have an account. API responses carry `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`. curl and lsb-release leave the image after the build. <!-- for: staff -->
- **Web app images hardened**: the four web app images (club app, manage, SSO, support) send Strict-Transport-Security on HTTPS (env `HSTS`, `off` to disable), no longer show the nginx version, and install their npm packages without install scripts. Their Permissions-Policy now allows the camera for the page itself, so the Keys check-in can scan badges again. The unused `app/deploy/Caddyfile` is gone. **Operators:** nginx now runs as a non-root user and listens on **8080** inside the container (compose and the Traefik labels are updated; a k8s Service or Ingress needs targetPort 8080, `LISTEN_PORT` changes it). A read-only root filesystem works with `/tmp`, `/var/cache/nginx`, `/usr/share/nginx/html` and `/etc/nginx/conf.d` as writable volumes. `X-Forwarded-Proto` counts only from private addresses or `REAL_IP_FROM`. The images install Alpine fixes at build time, and the image build now fails on fixable HIGH/CRITICAL CVEs in them. Images in posts from other websites load only after a click, so those sites don't learn who reads the post.
- **Club mail shows the club, account mail shows Hubra**: club mails (invites, events, polls, invoices, reminders, weekly digest, trial bookings, statements) now take the club's name, logo and main colour from Settings › Verein: buttons, links and the info box are in the club's colour (with dark button text on a light colour), and the inbox shows the club's name as sender. Some clubs got "Hubra" as their name because of an old seeded `club.name` setting; that value no longer names a club. Mails about the person's Hubra account (password, email confirmation, new sign-in, an existing account, club requests, closed account) and platform alerts and support answers always look like Hubra, even when a club's page sent them.
- **Sponsored clubs were still charged**: a club that already paid through Stripe kept being billed in full after manage marked it as sponsored. Now its subscription runs to the end of the period already paid and then ends (taken back if the sponsorship ends before that). While a sponsor pays, Settings › Hubra-Abo, Zusatzmodule and Settings › Module no longer say add-ons go on the next invoice, but who covers the cost. A club manage set to "not billed" (status none) can no longer start Checkout either.
- Customising Dashboard › Verein failed, and "Offene Rechnungen" couldn't be added to a dashboard: widget types with capital letters were refused.
- **Forms pass**: dropdowns no longer empty themselves when the chosen entry is clicked again (the page-size picker under lists could go to 0); searchable dropdowns say "Keine Ergebnisse." when nothing matches; "Kategorie wählen …"-style entries are placeholders, not choices. Dialogs share one footer (Abbrechen, then the main action; delete at the left) and save on Enter, in the club app and in manage. Money fields use one style (CHF, two decimals, no arrows), event places are number fields, and Settings › Erweitert uses the app's own checkboxes and filter.

## [0.2.5] - 2026-11-10

### Added

- **Standard roles and module access** (Settings › Roles, docs/roles.md): every club has Mitglied, Vorstand, Aktuar/in and Kassier/in, and the functions Präsident/in and Vizepräsident/in (Admin and Vorstand), Aktuar/in (Vorstand and Aktuar/in) and Kassier/in (Vorstand and Kassier/in). A function can now give several roles. Each role has one level per module; "None" hides the module from its holders everywhere (sidebar, pages, tabs, widgets, search, API `403 MODULE_ACCESS`), while their own invoices, claims and items stay on their profile. Plugins can give the standard roles access when a club first switches them on (`role_defaults`). Operators: run `flask db upgrade` and `flask seed`; the first `flask seed` adds the standard set to every club and keeps every role's modules.
- **Member badge on My Account** (sso › My account › Profile): one badge per person with a badge number such as `HB-7K3M-Q9TX`, the same in every club, and below it each membership with its tier, kind (honorary, passive) and member-since date. The number is random, given the first time the badge is shown (new column `users.badge_code`; run `flask db upgrade`).
- **Personal details on My Account** (sso › My account › Profile): first and last name, gender (new column `users.gender`), birthday, phone, mobile and address, edited by the person for all their clubs. The member badge also shows the badge number as a QR code.
- **Notification settings on My Account** (sso › My account › Notifications › Settings): per club and topic, choose bell, push, e-mail or Discord, the same choices as the club's own account page.
- **Your own sidebar categories**: in Customise sidebar you can add categories of your own (New category), rename any heading with the pencil, and remove your categories again; their pages go back to their own areas. The arrows move pages into and out of them. Saved on your account, like the rest of your sidebar.
- manage › Translations › Settings: the DeepL key and address for machine translation of posts can now be set in manage (before they had no field).
- Plugins can add sub-tabs to Finanzen › Rechnungen (plugin tab `group: 'invoices'`), such as settling the Kasse plugin's tab.
- **Plugins can take over another plugin**: a plugin that names another one under `replaces:` takes it over when it is installed or updated, with its data, module switches and permissions. The Plugin catalogue shows what an update takes over and hides the plugin it replaced. This is how Budgets becomes part of Finances (docs/plugins.md).
- **Own membership fees for single members**: on a member's page the board can exempt them from the fee, set their own yearly fee, or reduce the standard fee by a percentage, always with a reason and optionally until a date. Before that date (30 days by default) the member is asked in the app and by mail to confirm that the reason still applies; they answer under Account › Membership and the board is notified. After the end date the standard fee applies again from the next billing period. Members › Tiers lists all own fees. New rights `tiers.fee_adjustments.read` / `.update` (Treasurer in new clubs). See docs/club-admin-guide.md, "Own fees".
- **Modules can be renamed**: a module that names its old codes (`renamed_from`) keeps each club's switch and settings from the old code. This is how Guides becomes Qualifications without clubs switching it on again (docs/plugins.md).
- **Einstellungen button on Events, Posts and Polls**: admins open the module's settings (notifications, reminders, event types) straight from the page.
- **Plugins can name their own settings page** (`settings_page=` in the module manifest): Settings › Modules then links there instead of showing a second form, the way it already did for Finance (docs: app/backend/hubra/modules/README.md).
- manage › Platform: one page for what every app links to, the legal pages (privacy, terms, imprint) and the support site address. They were under Payments and Reports & ideas.

### Changed

- Finance › Settings now holds the fee basis (Beitragsgrundlage), next to the fee schedule; it was a tab under Budget & fees. Old links still open it.
- Settings › "API & Apps" is now called "API & Webhooks", so it no longer reads like Connected apps next to it.
- **More shows only what is not in the sidebar**: the More page in the club app now lists just the pages you moved out of the sidebar, grouped by area, instead of repeating every sidebar entry. With everything in the sidebar it says so and points to Customise sidebar.
- **Club switcher in the top bar**: the club name and logo at the top left now open a menu of all your clubs (with your role, the current one ticked) and a link to find another club. It replaces the club list in the account menu and works on phones too.
- **Settings in one place per page**: in manage, every page with platform settings ends with a "Settings" tab (All clubs, Alerts, Diagnostics, Backups, Mail, Discord, Translations, API tokens); Mail's Relay and System sender tabs and Discord's Setup and Channels tabs are now one Settings tab each. Old addresses redirect. In the club app, the Finance module's "Settings" button under Settings › Modules opens Finance › Settings instead of a second form for the same values, and `/app/settings/modules?module=<code>` opens a module's settings directly. See docs/settings/structure.md.
- **Cancel the Hubra subscription in Hubra**: Settings › Hubra subscription has *Cancel subscription* (it runs to the end of the paid period, then ends) and *Take cancellation back*, whatever the Stripe portal allows. In manage, switching a club to or from sandbox now ends its running subscription in the old Stripe mode at once; a club that paid live gets a sandbox subscription with the same lines instead of a refusal.
- **Plans: "Clubs can pick it" apart from "On the website"**: manage › Plans has two switches, so a plan can be on the pricing page without clubs picking it themselves, or the other way round. Existing public plans stay selectable. Operators: run `flask db upgrade`.

## [0.2.4] - 2026-11-06

### Added

- **Changelogs on Discord, for Hubra and for plugin updates**: each new Hubra version and each new plugin version is announced once, with its changelog section. Clubs opt in on their own Discord server (Discord settings › Announcements: "Changelog: new Hubra versions" and "Changelog: plugin updates", both off by default) and pick the channel, for example an announcements or a dedicated changelog channel; plugin updates only reach clubs that use that plugin. Hubra's own server gets them in the new changelog channel (manage › Discord, platform log card). They travel as the new events `hubra.released` and `plugin.released`, through the outbox, and are never posted twice. See docs/discord.md, "Changelogs".
- Licences go to members: for a module priced per licence the club assigns each licence to a member (Settings › Hubra subscription › Assign). Only holders see and use the module; everyone else gets "licence required".
- Hubra subscription: clubs see a full breakdown (quantities per member or licence, what the plan includes), switch to another public plan, and take or drop paid add-on modules with their licences under Settings › Hubra subscription. Settings › Modules shows the price of paid modules; switching one on asks first and books it.
- Hubra fee (formerly platform fee) on online payments per club: manage › All clubs › club › Billing can set a club's own percentage instead of the default; the club sees it on its subscription tab.
- Hubra subscription: clubs set the email and address for Hubra's invoices under Settings › Hubra subscription › Billing details; saving updates Stripe at once.
- Plans can build on each other: in manage › Settings › Plans a plan can optionally build on a lower plan and then includes all its modules plus its own ("Everything in Starter, plus …"). Plans can also be offered to chosen clubs as a custom plan, which those clubs can pick themselves under Settings › Hubra subscription.

### Changed

- **Sandbox and live Stripe keys, sandbox clubs**: Online payments and Hubra's billing each take a live key and a sandbox key (and billing a webhook secret for each), and manage › Payments has a Stripe mode switch, Sandbox or Live (default Sandbox). Sandbox clubs (manage › club › Sandbox club, or when creating a club) are demo and test clubs: they always use the sandbox keys, even when the platform is live, and are left out of revenue. Stripe's ids are kept per mode, and webhook events from the other mode are ignored. A test key stored in the old single key field keeps working as the sandbox key. See docs/billing.md, "Sandbox and live".
- Hubra subscription: changes during the month are billed pro rata on the next invoice (a member who joins, an add-on taken, a plan change; credits for the reverse). Only the subscription items that changed are updated in Stripe.
- **Releases carry their changelog**: the GitHub release of a Hubra version shows that version's changelog section as its description and has it attached as `CHANGELOG.md` (also in `SHA256SUMS`). ### Changed

Database statements stop after 60 s in the API and 5 min in workers, and a forgotten open transaction after 2 min. The event's own `event_id` now wins.
- **Trial trainings no longer overbook**: a booking confirmed after its 24-hour hold ran out only counts if a place is still free (the page says the training is full otherwise), and someone invited to join keeps their place. Old bookings are deleted by a daily job instead of when someone opens the trainers' list. The member statistics answer 400 instead of an error for a reference day out of range.
- **Sign-in and manage no longer run plugin code**: the global and platform backends and the platform worker read installed plugins' manifests (catalogue, migrations, tables, public plugin list) but no longer import their routes, models or task modules, so a broken plugin can only affect the club app backend. Manage's list of guarded endpoints shows plugin permissions from the permission catalog, without path and method. See docs/platform-backend.md.
- **A plugin whose code no longer fits Hubra no longer stops the backends from starting**: an installed Guides older than 1.2.0 imports `hubra.api.inventory`, which Hubra no longer has, and every backend (club, sign-in and platform) exited on start. A plugin whose routes fail to import is now skipped and logged as not loaded, like other plugin errors. The worker now imports plugins' Celery task modules after it has started, one by one, so one that fails only loses its own tasks instead of stopping the club and platform workers; the same holds for plugin routes that can't be registered, such as a blueprint name another plugin already uses.
- **Plugins with routes were refused after the OAuth change** ("route prefix overlaps / of core"): the blueprint for the OAuth `/.well-known` metadata has no prefix, so the plugin check saw core owning the whole site. A core blueprint on the site root is now treated like an area root and blocks no plugin.
- **Plugins with routes load again**: since the OAuth metadata route (`/.well-known/...`) joined core as a blueprint at the root, the plugin limits counted it as owning every path and refused every plugin with routes ("route prefix ... overlaps / of core"). Root blueprints no longer count.
- **Club search on the sign-in site works again**: after the API split the search asked a path no backend serves (`/api/v1/platform/system/clubs`), so it failed with a CORS error and found no clubs. It uses `/api/v1/global/clubs` again, and a test now checks that every path the apps call has a route.
- **Finance pages failed for clubs created before the recurring-transaction and invoice-period changes**: those two migrations changed only the template tables, so older clubs had no `transactions.recurring_id`, `invoices.period_start`/`period_end` or `recurring_transactions` table, and Transactions, Invoices and My invoices answered a server error. A migration adds what is missing, and every start now runs `flask sync-tenant-schemas`, which adds any table or column a club schema lacks (it never drops anything).
- **Diagnostics showed no running processes and a stale health cache after one slow Redis answer**: reading the build reports now waits up to a second and reports "unknown" instead of "not reporting", and a slow read no longer hides the health cache or lets the upgrade check decide from the worker's own build alone.
- **The Discord status read through an API token** (the Claude connector) gave the backend's in-cluster address as the expected interactions URL. Without `API_PUBLIC_URL` it is now unknown in that case.
- **Platform roles were empty**: manage › Rollen showed no platform roles and an empty permission list, so no permission could be given to a role. The platform permissions and default roles were only written by `flask seed-global-rbac`, which no deployment ran. `flask sync-permissions` (run on every start) now writes them too. Default roles: Platform admin, Manager, Support, the new Read-only, and Requester. A default role that already exists keeps the permissions it has; only Platform admin, whose permissions are locked, is completed on each start.
- **Discord security ping for platform admins on a new device** was never sent after an account sign-in (SSO, manage): it waited for a commit that came before it. It is now queued before that commit.
